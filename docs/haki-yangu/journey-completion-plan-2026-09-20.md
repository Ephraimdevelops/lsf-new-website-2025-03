# Journey-by-journey completion plan — Haki Yangu

## Working rule

Finish one user's complete route before starting the next. A journey is complete only when its screens, backend writes and reads, permissions, status transitions, errors, notifications and recovery paths work across web and mobile where promised. Screenshots supplied by the owner guide the interaction and visual design, not legal facts or provider records. Each phase ends with multi-account scenario QA and device/browser visual review; a passing build alone never closes a phase.

## 1. Beneficiary — Ask for Help and Find Help (current phase)

1. Entry and choice: distinct Ask for Help and Find Help routes; issue, location, service and language carry forward. Guests can explore; protected submissions require sign-in and restore a safe draft.
2. Find Help: verified public directory, filters and match explanation, service detail, contact, save/unsave, no-result path, and direct escalation to an LSF request. No confidential shelter/contact is exposed. Check contacts and hours against LSF-maintained records.
3. Ask for Help: guided story, issue, location, urgency/safety, desired help, documents, consent, review, draft, submit with idempotency, confirmation/reference, and staff triage context. Saada may clarify or explain, but cannot silently submit, share or refer.
4. Case journey: review status, matching/assignment, safe messages, appointment requests, document requests, beneficiary referral consent, response tracking, outcome, review/reopen request and feedback. Profile links to requests, cases, saved services, documents, appointments, language and privacy.
5. Closure evidence: separate beneficiary and LSF/provider accounts run employment, land, family, safety and no-local-service scenarios on web and phone; validate storage, notifications, privacy, offline retry and accessibility.

Status: **in progress**. Category/service context, saved services, and an explicit user-reviewed Saada-to-request draft are connected in code. Referral proposals now remain inactive until the beneficiary approves the named public destination and information list on mobile or web; a decline leaves the provider uninformed. Onward proposals use the same gate. The image-level map/compare/check-in features, full device and multi-account QA, consent-language review, and real verified service inventory are open.

## 2. Saada — beneficiary assistant and governed knowledge

Conversational help, multilingual clarification, sourced legal explanations, district-aware directory lookup, safe transfer into an explicit user-reviewed request, human escalation and unsafe-answer handling. Admin source upload, provenance, version, independent approval, retrieval-only-after-approval, prompt versioning, flagged-response review, evaluation set and audit trail. Close only after Tanzania legal review and adversarial/high-risk scenario QA.

## 3. Paralegal — application to daily work

Invitation/application, identity and organisation review, approval, role activation, onboarding checklist, training/ethics, verified public profile, availability, assignment offers, scoped case workspace, secure messages and documents, appointments, tasks, referral work, notes, outcomes and support. Close after a real beneficiary/provider two-account case run and access revocation test.

## 4. LSF and partner governance

Operations triage, matching supervision, safeguarding, service directory verification, provider governance, user/role approvals, Saada source/prompt governance, audit access, reporting and donor-safe exports. Close after approval separation, organisation-scoped permission tests, privacy/retention review and full operational rehearsal.

## Release gate

Run complete cross-role journeys on actual configured web origin and device builds. Verify sources and contacts with LSF, conduct Tanzania legal/safeguarding review, test notifications/offline/accessibility/security, and make a release decision from evidence. Do not report 98–99% until these gates pass.
